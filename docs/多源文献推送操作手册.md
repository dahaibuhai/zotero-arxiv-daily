# 多源文献推送操作手册（arXiv + Semantic Scholar）

本 fork 在上游 `Zotero-arXiv-Daily` 的基础上增加了可面向任意研究方向的多源文献推送能力。研究者只需替换自己的 arXiv 分类、关键词和 Semantic Scholar 查询词，就能用于材料、物理、化学、生命科学、人工智能、数学或交叉方向；系统不会把研究领域写死在 Python 逻辑里。

当前 workflow 中预置的是磁控溅射/PVD 示例词表，**它只是一个可替换的样例，不是系统限制**。自定义功能与上游功能的来源和提交历史见[上游与自定义改造清单](上游与自定义改造清单.md)。

## 1. 当前流程

```text
arXiv ───────────────┐
Semantic Scholar ────┼─> 统一去重 ─> 已发送历史过滤 ─> 关键词筛选/加权
Crossref（可选）─────┘                                      │
                                                            v
Zotero 文献库 ─────────────────────────────────────> 相似度重排 ─> 邮件 ─> 写回发送历史
```

- **arXiv**：根据 `ARXIV_QUERY` 检索目标分类中新发布的预印本。
- **Semantic Scholar**：根据自定义查询词补充期刊论文和非 arXiv 记录；当前 workflow 默认启用。
- **Crossref（可选）**：按指定期刊 ISSN 抓取新论文。它不依赖研究领域，但只建议在已有明确期刊目录时启用。
- **统一去重**：优先使用 DOI、论文 ID 或规范化题名识别跨来源重复。
- **历史去重**：最近 90 天内已实际发出的论文不再重复推送。
- **关键词加权**：相关词提高排序，排除词直接移除；随后再与 Zotero 文献库相似度合并排序。

## 2. 首次配置

### 2.1 必须使用自己的 fork

进入 **Settings → Secrets and variables → Actions → Variables**，检查 `REPOSITORY` 与 `REF`：

- 要运行本仓库的多源自定义代码时，两者应保持**未设置或为空**。
- 如果 `REPOSITORY` 指向上游仓库，Actions 会检出上游代码；Semantic Scholar、Crossref、关键词筛选和发送历史不会生效。

### 2.2 Secrets

在 **Settings → Secrets and variables → Actions → Secrets** 中设置敏感配置。不要把这些值写进 workflow、文档或提交记录。下表前三行是当前日常推送的必需项；LLM API 及 Semantic Scholar 密钥均为可选项。

| Secret | 用途 |
|---|---|
| `ZOTERO_ID`、`ZOTERO_KEY` | 读取 Zotero 文献库，构成个性化排序语料 |
| `SMTP_SERVER`、`SMTP_PORT` | 发件服务器与端口 |
| `SENDER`、`SENDER_PASSWORD`、`RECEIVER` | 发件人、授权码和收件人 |
| `USE_LLM_API`、`OPENAI_API_KEY`、`OPENAI_API_BASE`、`MODEL_NAME` | **可选**：仅在用 API 生成 TLDR 时需要；未设置时不要创建这些 Secret |
| `SEMANTIC_SCHOLAR_API_KEY` | 可选；为空时自动使用匿名访问 |

### 2.3 TLDR 生成方式：默认无需 API

当前工作流没有设置 `USE_LLM_API`，所以会使用项目自带的本地 Qwen 模型生成 TLDR。此时**不需要**设置 `OPENAI_API_KEY`、`OPENAI_API_BASE` 或 `MODEL_NAME`；workflow 中保留这些空的 Secret 引用不会影响运行。

只有准备改用 OpenAI 兼容 API 时，才在 Secrets 中同时设置以下四项：

| Secret | 示例 | 说明 |
|---|---|---|
| `USE_LLM_API` | `true` | 显式切换到 API 模式 |
| `OPENAI_API_KEY` | 服务商提供的密钥 | 不要提交到仓库 |
| `OPENAI_API_BASE` | `https://api.openai.com/v1` | 所用服务的兼容 API 地址 |
| `MODEL_NAME` | `gpt-4o` | 所用服务支持的模型名 |

不要只设置后三项而不设置 `USE_LLM_API=true`；那样仍会使用本地模型。

### 2.4 通用 Variables

在 **Settings → Secrets and variables → Actions → Variables** 中设置：

| Variable | 建议起点 | 说明 |
|---|---:|---|
| `ARXIV_QUERY` | 目标分类，用 `+` 连接 | 例如 `cs.AI+cs.LG`；请从 [arXiv 分类表](https://arxiv.org/category_taxonomy)选择本方向分类。 |
| `MAX_PAPER_NUM` | `10` | 一封邮件的最大论文数；越大，TLDR 生成越慢。 |
| `SEND_EMPTY` | `False` | 没有候选时是否发送空邮件。 |
| `LANGUAGE` | `Chinese` | TLDR 输出语言。 |
| `ZOTERO_IGNORE` | 按需填写 | 每行一条要从排序语料中排除的 Zotero 分类规则。 |

> 在此 fork 中，`ARXIV_QUERY`、`MAX_PAPER_NUM` 和 `SEND_EMPTY` 从 **Variables** 读取，不是 Secrets。

## 3. 为任意研究方向创建检索配置

### 3.1 配置位置

关键词和 Semantic Scholar 查询词当前位于两个 workflow 的 `Run script → env` 区域：

- [`.github/workflows/main.yml`](../.github/workflows/main.yml)：正式定时推送。
- [`.github/workflows/test.yml`](../.github/workflows/test.yml)：手动测试。

两处必须同步修改。当前的 PVD/薄膜/HiPIMS 词表只是样例；切换研究方向时应**整体替换**该样例，而不是在其后持续叠加新方向的词。

### 3.2 通用配置模板

下面是结构模板；将尖括号内容替换为自己领域的词。建议先从少量高确定性术语开始。

```yaml
KEYWORD_FILTER_MODE: boost
KEYWORDS_BOOST: |
  <核心研究主题>:6
  <常用同义词>:5
  <关键方法或材料体系>:4
  <应用场景或对象>:3
KEYWORDS_REQUIRE: ""
KEYWORDS_EXCLUDE: |
  <明确无关主题 1>
  <明确无关主题 2>
KEYWORD_BOOST_WEIGHT: "1.5"

ENABLE_SEMANTIC_SCHOLAR: "true"
SEMANTIC_SCHOLAR_QUERIES: |
  "<核心主题>" "<限定词>"
  "<同义词或缩写>"
  "<方法>" "<研究对象>"
SEMANTIC_SCHOLAR_DAYS: "7"
SEMANTIC_SCHOLAR_MAX_RESULTS_PER_QUERY: "5"
```

建议顺序：

1. 选择 1–3 个准确的 arXiv 分类，写入 `ARXIV_QUERY`。
2. 为 `KEYWORDS_BOOST` 写 5–20 个核心概念、同义词、方法词或对象词，并给核心短语更高权重。
3. 为 `SEMANTIC_SCHOLAR_QUERIES` 写 3–8 条短查询；一行就是一次 API 查询。
4. 只向 `KEYWORDS_EXCLUDE` 加入明显错误方向，避免用大量负词硬凑相关性。
5. 先运行测试工作流；确认质量后再扩大查询词或时间窗口。

### 3.3 关键词行为

- `KEYWORDS_BOOST`：每行格式为 `关键词:权重`。题名或摘要命中后会增加分数；不命中时，在 `boost` 模式下仍保留论文。
- `KEYWORDS_EXCLUDE`：每行一个短语；命中即剔除论文。
- `KEYWORD_FILTER_MODE = boost`：推荐默认值，适合探索新词和跨学科论文。
- `hard`：仅当同时填写 `KEYWORDS_REQUIRE` 时才会硬筛选；设置 `hard` 但让 `KEYWORDS_REQUIRE` 为空不会过滤任何论文。
- `KEYWORD_BOOST_WEIGHT`：关键词分数与 Zotero 相似度合并前的全局倍率。若关键词主导排序，可从 `1.5` 调低到 `1.0`。

### 3.4 Semantic Scholar 行为

每行 `SEMANTIC_SCHOLAR_QUERIES` 都独立执行。匿名模式可用；若 API key 无效，程序会自动降级匿名访问。遇到 `429`、`5xx` 或网络超时会退避重试；一条查询最终失败只跳过该条，不会中断整封邮件。

开始时建议保持最近 `7` 天、每条最多 `5` 篇；需要更大覆盖面时，先增加查询词，再逐步增加时间窗或每条上限。

## 4. 可选：启用 Crossref 期刊目录

Crossref 适合以下情况：目标论文主要发表在少量已知期刊，或该领域 arXiv 覆盖率低。它不是使用 arXiv + Semantic Scholar 的必要条件。

在 **Variables** 中新增或修改：

| Variable | 首次测试建议 | 说明 |
|---|---:|---|
| `ENABLE_CROSSREF` | `True` | 启用期刊目录抓取。 |
| `CROSSREF_DAYS` | `30` | 首轮可设为 30；稳定后改回 7。 |
| `CROSSREF_ROWS_PER_JOURNAL` | `5` | 每本期刊最多读取的记录数。 |
| `CROSSREF_MAILTO` | 有效联系邮箱 | 礼貌访问 Crossref；不需要 API key。 |
| `CROSSREF_JOURNALS` | 见下方 | 每行 `期刊名|ISSN|期刊权重`。 |

格式示例：

```text
<Journal A>|<ISSN>|2
<Journal B>|<ISSN>|1.5
```

Crossref 记录常缺摘要，因此本项目要求它至少命中一个正向关键词才会保留。先只加入 2–7 本最核心期刊；若噪声高，先减少期刊或每刊条数，不要只增加排除词。

## 5. 验证一次配置改动

1. 只修改一组参数，例如先改关键词，或先改 Semantic Scholar 查询词。
2. 进入 **Actions → Test workflow → Run workflow**。
3. 在 `Run script` 日志中检查：

   ```text
   Retrieving Arxiv papers...
   Retrieving Semantic Scholar papers...
   Remaining N papers after deduplication.
   Remaining N papers after excluding K previously sent papers.
   Remaining N papers after keyword filtering.
   Email sent successfully!
   ```

4. 检查邮件前几篇是否符合研究方向，并确认 `Keyword hits`、`Source`、`Venue` 和论文链接正确显示。

测试 workflow 使用 `.tmp/sent_history_test.json`，不会污染正式 90 天历史。当前测试模式的 arXiv 部分固定提取 5 篇 `cs.AI` 论文，因此它适合检查通路；要验证自己分类的 arXiv 新论文，可在配置完成后手动运行一次正式 `Send emails daily` workflow。

## 6. 定时推送与历史去重

正式工作流使用：

```yaml
- cron: '30 1 * * 1-5'
```

即工作日北京时间约 09:30 触发；GitHub runner 排队可能导致实际启动时间略有浮动。

正式邮件发出成功后，程序将记录到 `data/sent_history.json`，工作流会把该文件提交回 `main`。日志中应出现：

```text
Recorded N delivered papers in sent history (data/sent_history.json).
```

当前正式流程固定使用 `SENT_HISTORY_PATH=data/sent_history.json` 和 `SENT_HISTORY_DAYS=90`。若确实要改变期限，应同步修改两个 workflow；测试流程必须保留 `.tmp/sent_history_test.json`。

## 7. 常见现象

| 现象 | 含义与处理 |
|---|---|
| 工作流成功但没有邮件 | 候选可能在关键词或历史过滤后为空，且 `SEND_EMPTY=False`；检查 `No new papers found`。 |
| `arXiv retrieval failed; continuing with other sources` | arXiv 临时不可用或限流；流程会继续处理其他来源。 |
| `Skipping Semantic Scholar query after retries` | 单条查询限流或网络失败；等待 20–60 分钟，或减少查询数量。 |
| 推荐不够相关 | 先收紧 Semantic Scholar 查询、提高核心关键词权重；不要立即改为硬筛选。 |
| 推荐太少 | 增加同义词、相邻分类或少量查询词；必要时再启用 Crossref。 |
| 重复论文再次出现 | 确认日志同时包含 `Email sent successfully!` 和 `Recorded N delivered papers...`。 |
| 改了配置但邮件无变化 | 检查 `REPOSITORY` / `REF` 是否让 workflow 检出了上游代码，并确认 `main.yml` 与 `test.yml` 已同步。 |

## 8. 调参原则

每次只改一个变量组，并记录各来源原始数、历史去重数、关键词过滤后数量和邮件前 3 篇标题。

1. 先稳定 arXiv 分类与关键词。
2. 再调 Semantic Scholar 查询词。
3. 最后才启用或扩充 Crossref。
4. 每次先跑 `Test workflow`，随后观察至少一次正式邮件。

这样才能判断推荐质量的变化来自哪个来源或配置项，也能安全地撤回单项调整。
