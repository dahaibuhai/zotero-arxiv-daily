# 材料文献推送操作手册

本仓库在原始 `Zotero-arXiv-Daily` 的基础上，面向磁控溅射、PVD、薄膜、HiPIMS、钼靶/高温靶和相关模拟研究增加了多源抓取、关键词排序、历史去重与容错机制。本手册只说明这套自定义流程；通用的 Zotero、SMTP 和 LLM 配置仍可参考根目录 [README](../README.md)。

## 1. 当前流程

```text
arXiv ───────────────┐
Semantic Scholar ────┼─> 统一去重 ─> 已发送历史过滤 ─> 关键词筛选/加权
Crossref（可选）─────┘                                      │
                                                            v
Zotero 语料 ───────────────────────────────────────> 相似度重排 ─> 邮件 ─> 写回发送历史
```

- arXiv：保留预印本发现能力。
- Semantic Scholar：补充期刊论文与非 arXiv 记录；当前工作流默认启用。
- Crossref：按指定期刊 ISSN 补充新论文；默认关闭，需按第 5 节自行启用。
- 统一去重：优先用 DOI、论文 ID 或规范化题名识别跨来源重复记录。
- 历史去重：成功发信后记录论文；90 天内已发送论文不再重复推送。
- 关键词加权：相关词提升排序，排除词直接剔除；最终再与 Zotero 文献库相似度合并排序。

## 2. 首次配置前的关键检查

### 使用自己的 fork

进入 GitHub 仓库的 **Settings → Secrets and variables → Actions → Variables**，检查 `REPOSITORY` 和 `REF`：

- 要运行本仓库的自定义代码时，两个变量应保持**未设置或为空**。
- 如果 `REPOSITORY` 指向 `TideDra/zotero-arxiv-daily`，工作流会检出上游代码；本仓库新增的关键词、Semantic Scholar、Crossref 和历史去重流程都不会生效。

### 必要 Secrets

在 **Settings → Secrets and variables → Actions → Secrets** 中保留以下敏感配置。不要把这些值写进 workflow、文档或提交记录。

| Secret | 用途 |
|---|---|
| `ZOTERO_ID`、`ZOTERO_KEY` | 读取 Zotero 文献库，用作个性化排序语料 |
| `SMTP_SERVER`、`SMTP_PORT` | 发件服务器与端口 |
| `SENDER`、`SENDER_PASSWORD`、`RECEIVER` | 发件人与收件人配置 |
| `OPENAI_API_KEY`、`OPENAI_API_BASE`、`MODEL_NAME` | 仅在启用 API 生成 TLDR 时需要 |
| `SEMANTIC_SCHOLAR_API_KEY` | 可选；为空时自动使用匿名访问 |

### 日常 Variables

在 **Settings → Secrets and variables → Actions → Variables** 中设置或检查：

| Variable | 推荐起点 | 说明 |
|---|---:|---|
| `ARXIV_QUERY` | `cond-mat.mtrl-sci+physics.plasm-ph+physics.app-ph` | 多个 arXiv 分类用 `+` 连接；不要一开始加过宽的分类。 |
| `MAX_PAPER_NUM` | `10` | 邮件中的最多论文数；越大，TLDR 生成越慢。 |
| `SEND_EMPTY` | `False` | 没有候选论文时不发空邮件。 |
| `LANGUAGE` | `Chinese` | TLDR 语言。 |
| `ZOTERO_IGNORE` | 按需填写 | 每行一条 Zotero 分类忽略规则。 |

> `ARXIV_QUERY`、`MAX_PAPER_NUM` 和 `SEND_EMPTY` 在此 fork 中由 **Variables** 读取，不是 Secrets。

## 3. 修改研究主题：关键词与 Semantic Scholar

当前材料研究默认配置写在两个文件的 `Run script → env` 区域中：

- [`.github/workflows/main.yml`](../.github/workflows/main.yml)：正式定时推送。
- [`.github/workflows/test.yml`](../.github/workflows/test.yml)：手动测试。

修改研究主题时，两个文件必须同步修改；否则测试邮件和每日邮件会使用两套不同的检索规则。

### 关键词加权与排除

配置项如下：

```yaml
KEYWORD_FILTER_MODE: boost
KEYWORDS_BOOST: |
  magnetron sputtering:6
  high power impulse magnetron sputtering:6
  sputtering yield:6
  molybdenum:5
  thin film stress:6
KEYWORDS_EXCLUDE: |
  water electrolysis
  biomedical
  flexible sensor
KEYWORD_BOOST_WEIGHT: "1.5"
```

- `KEYWORDS_BOOST`：每行格式为 `关键词:权重`；命中题名或摘要就增加分数。优先调这一项，不要一开始加入大量排除词。
- `KEYWORDS_EXCLUDE`：每行一个明确无关主题；命中即丢弃。
- `KEYWORD_FILTER_MODE = boost`：不命中关键词的论文仍保留，但会排在后面，适合探索新词。
- `hard`：只有同时填写 `KEYWORDS_REQUIRE` 时才会真正硬筛选。设置 `hard` 但让 `KEYWORDS_REQUIRE` 为空不会过滤任何论文。
- `KEYWORD_BOOST_WEIGHT`：关键词分数与 Zotero 相似度合并前的全局倍率。若关键词排序过强，可从 `1.5` 降到 `1.0`；不要同时大幅改关键词和倍率。

### Semantic Scholar 定向查询

当前正式流程已启用 Semantic Scholar：

```yaml
ENABLE_SEMANTIC_SCHOLAR: "true"
SEMANTIC_SCHOLAR_DAYS: "7"
SEMANTIC_SCHOLAR_MAX_RESULTS_PER_QUERY: "5"
SEMANTIC_SCHOLAR_QUERIES: |
  "magnetron sputtering" "thin film"
  "high power impulse magnetron sputtering"
  "sputtering yield" "molecular dynamics"
```

每行是一条查询。建议一次只增加 1–2 条，连续观察一周后再决定是否保留；查询过多会增加 API 限流概率和邮件噪声。

匿名模式可用。若配置了无效 API key，程序会先尝试认证访问，再自动降级为匿名访问。遇到 `429`、`5xx` 或网络超时时会退避重试；某一条查询最终失败只会跳过该查询，不会中断整封邮件。

## 4. 验证关键词与 Semantic Scholar 改动

1. 先只修改两个 workflow 中相同的一组 `env` 配置。
2. 进入 **Actions → Test workflow → Run workflow**。
3. 在 `Run script` 日志中检查以下顺序：

   ```text
   Retrieving Arxiv papers...
   Retrieving Semantic Scholar papers...
   Remaining N papers after deduplication.
   Remaining N papers after excluding K previously sent papers.
   Remaining N papers after keyword filtering.
   Email sent successfully!
   ```

4. 检查邮件前几篇是否命中预期主题，以及是否显示合理的来源/链接。

测试 workflow 会使用 `.tmp/sent_history_test.json`，不会污染正式的 90 天发送历史。测试模式的 arXiv 部分固定取 5 篇 `cs.AI` 论文，因此它主要用来检查流程是否通畅；研究主题相关性应重点观察 Semantic Scholar 结果和随后的正式邮件。

## 5. 启用 Crossref 期刊目录

Crossref 适合补充没有预印本的期刊论文。先在 **Variables** 中新增或修改：

| Variable | 首次测试建议 | 说明 |
|---|---:|---|
| `ENABLE_CROSSREF` | `True` | 启用期刊目录抓取。 |
| `CROSSREF_DAYS` | `30` | 首次测试可设为 30；稳定后改回 7。 |
| `CROSSREF_ROWS_PER_JOURNAL` | `5` | 每本期刊最多读取的记录数。 |
| `CROSSREF_MAILTO` | 有效联系邮箱 | 用于礼貌访问 Crossref；不需要 API key。 |
| `CROSSREF_JOURNALS` | 见下方 | 每行 `期刊名|ISSN|期刊权重`。 |

首轮可从下列 7 本期刊开始：

```text
Thin Solid Films|0040-6090|2
Surface and Coatings Technology|0257-8972|2
Vacuum|0042-207X|2
Journal of Vacuum Science & Technology A|0734-2101|2
Applied Surface Science|0169-4332|1.5
Plasma Sources Science and Technology|0963-0252|2
Nuclear Instruments and Methods in Physics Research Section B|0168-583X|2
```

然后运行一次 `Test workflow`，将 `CROSSREF_DAYS` 改回 `7` 后再观察正式邮件。日志应包含：

```text
Retrieving Crossref journal papers...
Retrieved N papers from Crossref.
Remaining M Crossref papers after title keyword gating (dropped K).
```

Crossref 条目常常没有摘要，因此本项目要求它至少命中一个正向关键词才会保留；这能避免宽口径期刊挤占邮件名额。若连续两周候选不足，再逐步添加 `Journal of Physics D: Applied Physics` 或 `Computational Materials Science`，不要一次扩展大量综合材料期刊。

## 6. 定时推送与发送历史

正式工作流定义在 `.github/workflows/main.yml`：

```yaml
- cron: '30 1 * * 1-5'
```

这表示工作日北京时间约 09:30 触发；GitHub runner 可能排队，因此实际开始时间会略有浮动。手动运行正式工作流也会执行真实历史去重。

发送成功后，工作流会把 `data/sent_history.json` 提交回 `main` 分支。日志中应看到：

```text
Recorded N delivered papers in sent history (data/sent_history.json).
```

正式 workflow 当前固定使用 `SENT_HISTORY_PATH=data/sent_history.json` 与 `SENT_HISTORY_DAYS=90`；一般不需要修改。若确实要改变去重期限，应同时修改 `main.yml` 和 `test.yml`，但测试 workflow 必须继续使用 `.tmp/sent_history_test.json`，以免测试邮件写入正式历史。

若该行出现但最后的 `Persist sent history` 失败，优先检查仓库 Actions 是否拥有 `contents: write` 权限，以及 `main` 分支保护规则是否禁止 GitHub Actions 直接推送。

## 7. 常见现象与处理

| 现象 | 含义与处理 |
|---|---|
| 工作流成功但没有邮件 | 可能是所有候选在关键词或历史过滤后为空，且 `SEND_EMPTY=False`；先检查 `No new papers found` 日志。 |
| `arXiv retrieval failed; continuing with other sources` | arXiv 临时限流或不可用；流程会继续使用其他来源，不必连续手动重跑。 |
| `Skipping Semantic Scholar query after retries` | 单条查询被限流或网络失败；先等待 20–60 分钟，再考虑减少查询数量。 |
| Semantic Scholar 结果太杂 | 收紧查询词、提高 `KEYWORDS_BOOST` 中核心词权重，或加入少量明确排除词。 |
| Crossref 噪声太多 | 先确认标题关键词门控日志，再减少期刊/每刊条数；不要仅靠堆叠排除词。 |
| 重复论文再次出现 | 检查是否有 `Recorded N delivered papers...`，并确认正式 workflow 的 `Persist sent history` 成功。 |
| 改了代码但邮件没有变化 | 优先检查 `REPOSITORY` / `REF` 是否让 workflow 检出了上游仓库。 |

## 8. 推荐的调参节奏

每次只改一个变量组，并记录测试日期、各来源原始数、历史去重数、关键词过滤后数量和最终邮件前 3 篇标题。

1. 先稳定关键词：只改 `KEYWORDS_BOOST`、`KEYWORDS_EXCLUDE` 或 `KEYWORD_BOOST_WEIGHT`。
2. 再稳定 Semantic Scholar：每周最多新增 1–2 个查询词。
3. 最后启用或扩充 Crossref：从 7 本首轮期刊和每刊 5 条开始。
4. 每次改动后先运行 `Test workflow`，再观察至少一次正式邮件。

这样能知道推荐质量变化是由哪个来源或配置项造成的，也便于回退单个设置。
